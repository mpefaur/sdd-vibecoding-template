## Karpathy principles — expanded

**1. Think Before Coding** — Don't assume. Don't hide confusion. Surface tradeoffs.
State assumptions explicitly. If a request has two plausible readings, present both and
ask — one question beats a wrong implementation. Name the tradeoff you took and what you
gave up.

**2. Simplicity First** — Minimum code that solves the problem. Nothing speculative.
No features that weren't requested. No abstraction with a single caller. No config flag
with one value. No error handling for errors that can't happen. YAGNI is the default.

**3. Surgical Changes** — Touch only what you must. Clean up only your own mess.
Match the surrounding style even if you'd write it differently. Don't refactor working
code you happened to read. Don't fix unrelated bugs, dead code, or formatting you didn't
create — report them instead.

**4. Goal-Driven Execution** — Define success criteria. Loop until verified.
Turn "make it work" into a checkable statement ("`pytest tests/auth` passes, login
returns 200"). Run it. If it fails, fix and re-run. Report only verified results.

## Workflow

Always Spec → Plan → Tasks → Implement. Concretely:

```
/kickoff                # once, on a fresh clone — adopts the template (see AGENTS.md §0)
/speckit-constitution   # once per project
/speckit-specify        # what & why  → creates branch + specs/<n>-<slug>/spec.md
/speckit-clarify        # resolve [NEEDS CLARIFICATION] before planning
/speckit-plan           # how → plan.md, research.md, contracts
/speckit-tasks          # tasks.md
/speckit-analyze        # cross-artifact consistency (read-only)
/speckit-implement      # build
/speckit-converge       # append unbuilt work; repeat implement ⇄ converge until Converged
```

Bugs: `/speckit-bug-assess` → `/speckit-bug-fix` → `/speckit-bug-test` (reports in
`.specify/bugs/<slug>/`). Tasks → GitHub issues: `/speckit-github-taskstoissues` (the core
`/speckit-taskstoissues` is deprecated upstream).

Do not write implementation code before `tasks.md` exists — except for one-line typo
fixes, answering questions, and fixes that went through the bug lane above.

## Implementation execution

`tasks.md` groups work into Setup, Foundational, then one phase per user story —
`tasks-template.md`'s own "Parallel Team Strategy" already says stories can proceed in
parallel once Foundational is done, it just assumes human developers. Once Foundational
completes, before parallelizing, diff the file paths listed across the ready story
phases:

- **Disjoint file sets across two or more stories** → run each story in its own worktree
  (`EnterWorktree`) driven by its own subagent, in parallel. Merge each worktree back
  into the feature branch **one at a time**, running the verification gate before each
  merge — never merge two stories concurrently, and never run two agents against the
  same working tree (concurrent `git add`/commit from separate subagents in one
  directory races on the git index — this is the exact failure GitHub Spec Kit's
  maintainers cited when they kept worktree orchestration out of spec-kit's core:
  `github/spec-kit#1476`).
- **Any file path shared across stories** (e.g., a router both stories register into) →
  those stories aren't independent regardless of the `[P]` marker — run them
  sequentially in the main session instead.

Within a single story, keep its own tasks — including ones marked `[P]` — in one agent /
one session. A story's tasks share tight context (its own models, service, tests);
splitting them by individual task adds coordination overhead without a real speed win.
Reserve subagent/worktree fan-out for units large and independent enough to amortize that
overhead — a user story is; a lone `[P]` task inside one story usually isn't.

This is execution strategy only, layered on top of `speckit-implement`. Keep it here, not
in `.claude/skills/speckit-*` or `.specify/` — those files are generated by Spec Kit and
overwritten on upgrade. Follow the task phases, hook checks, dependency order, and
completion criteria in `.claude/skills/speckit-implement/SKILL.md` as written.

## Response style

- Concise and technically exact. Lead with the answer or result; end a task with a short
  report of what changed and what verification showed, not a replay of every step.
- Code, commands, file paths and identifiers are **never** abbreviated — only prose is
  kept short.

## Shell commands

Prefer RTK over raw tools; it emits the same information with 60–90% fewer tokens.

| Instead of                | Use                             |
| ------------------------- | ------------------------------- |
| `ls -R`                   | `rtk ls`                        |
| `cat file`                | `rtk read file`                 |
| `grep -r pat`             | `rtk grep pat`                  |
| `find . -name`            | `rtk find <pat>`                |
| `git status` / `git diff` | `rtk git status` / `rtk git diff` |
| `npm test` / `pytest`     | `rtk test`                      |
| `eslint` / `ruff`         | `rtk lint`                      |
| noisy stack trace         | `rtk err <cmd>`                 |

Check the payoff with `rtk gain`. If RTK is not installed, fall back to the raw command —
never block on it.

## Before saying "done"

1. Ran `./scripts/verify.sh --full` (the `verify` skill) and read the actual output.
2. No secrets, keys, tokens, or `.env` values added to tracked files.
3. Diff contains only what the task required (Surgical Changes).
4. Commit message follows Conventional Commits.

If any check failed, say which one and what the output was. Never report success you
did not observe.

Checks 1 and 2 are also enforced by the harness — `.claude/hooks/verification-gate.sh`
on `Stop`, `permissions.deny` + the Bash sandbox and Betterleaks (pre-commit and CI) for
secrets. Never bypass a failing commit hook (`--no-verify`, `-n`, `SKIP=`). See
[docs/TEMPLATE_USAGE.md](docs/TEMPLATE_USAGE.md) §9. A green hook is not a substitute
for reading the output yourself.
